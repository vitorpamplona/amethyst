# Tor on iOS (B12)

Status: proposal, 2026-11-25. This expands step B12 of `commons/plans/2026-10-09-ios-app.md`.

Goal: the iOS app routes traffic through an embedded Tor client the way Android does. That means the
same settings, presets and per-role routing, `.onion` relays, status and the stuck dialog. Today
iOS has no Tor.

Notation: **verified** means checked on 2026-11-25, in this repo or at the URL cited. Anything else
is marked *unverified* or *estimate*.

---

## 0. Why this is urgent: the UI says Tor is on and nothing uses it

- `TorSettings()` defaults to `torType = TorType.INTERNAL`, and `TorSettingsStore` falls back to
  `TorType.INTERNAL` when the key is missing. Verified:
  `commons/src/commonMain/kotlin/com/vitorpamplona/amethyst/commons/tor/TorSettings.kt`, and
  `commons/src/commonMain/kotlin/com/vitorpamplona/amethyst/commons/model/preferences/TorSettingsStore.kt:104`.
- `IosAppModules` builds `TorSettingsStore(TorSettings(), …)`. Its comment says "the stored
  settings say off". That is wrong: they say INTERNAL with the default preset (onion, DM and new
  relays via Tor). But every connection goes direct through one `HttpClient(Darwin)`. Verified:
  `iosApp/src/iosMain/kotlin/com/vitorpamplona/amethyst/ios/IosAppModules.kt:147-163`.
- `IosAppServices.torBootstrapped` is `flowOf(false)`, and `IosAccountViewModelHost.torRelayEvaluation`
  is a constant `TorRelayEvaluation(TorRelaySettings())`. Verified.

So a user who opens Privacy › Tor on iOS sees Tor set to internal and believes their DM and unknown
relays go through Tor. They do not. **B12-0 below fixes this display first**, before any engine work.

## 1. How Android does Tor today

### 1.1 Engine: Arti, built in this repo

- **Library.** Arti (Tor in Rust), through our own JNI wrapper crate `tools/arti-build`. Verified
  in `tools/arti-build/Cargo.toml`:
  - crate `arti-android` 2.6.0;
  - `arti-client = 0.46` with features `tokio`, `rustls`, `compression`, `onion-service-client`,
    `static-sqlite`;
  - `tor-rtcompat 0.46`, `rustls 0.23` with the `ring` provider, and `jni 0.22`;
  - release profile `opt-level="z"`, LTO, `panic="abort"`.
- **Arti version.** `tools/arti-build/ARTI_VERSION` = `arti-v2.6.0`.
- **Toolchain.** Rust is pinned to 1.98.1 (`rust-toolchain.toml`). The NDK is pinned too, for
  reproducible builds (`tools/arti-build/README.md`).
- **Shipped binaries.** Committed `.so` files in `amethyst/src/main/jniLibs/<abi>/libarti_android.so`.
  Verified sizes: arm64-v8a 5.4 MB, armeabi-v7a 3.9 MB, x86 6.0 MB, x86_64 6.3 MB.
  `amethyst/build.gradle.kts` checks that every ABI ships one (`verifyNativeAbis`).
- **No Maven artifact for Android.** `libs.kmp.tor.runtime` and `libs.kmp.tor.resource.exec.tor`
  (kmp-tor runtime 2.6.0, resource 409.5.0) are used **only by `desktopApp`**
  (`desktopApp/build.gradle.kts:144-146`). Desktop runs C-tor as a child process: see
  `desktopApp/…/desktop/tor/DesktopTorManager.kt` and `ResourceLoaderTorExec`.
- **Host build.** `tools/arti-build/build-arti-host.sh` builds the same crate for macOS/Linux
  hosts, for `TorArtiNativeIntegrationTest`.

### 1.2 JNI surface: `amethyst/…/ui/tor/ArtiNative.kt` and `tools/arti-build/src/lib.rs`

| Call | Meaning |
|---|---|
| `initialize(dataDir)` | Creates the process-lifetime `TorClient` with `BootstrapBehavior::OnDemand`. It returns in about 130 ms, and the directory download runs in the background. |
| `isBootstrapped()` | Live readiness: 1, 0 or -1. |
| `bootstrapProgressPermille()` | Progress from 0 to 1000. Used for stall detection. |
| `startSocksProxy(port)` / `stopSocksProxy()` | An in-process SOCKS5 listener written in Rust (`handle_socks_connection`). Failures map to SOCKS reply codes (`socks_reply_for`). |
| `destroy()` | Aborts the bootstrap task, the SOCKS task and the handler tasks, and drops the client, so the state lock is released. |
| `setLogCallback` | Arti log lines go to Kotlin. They are used for `AllGuardsDown` detection. |

### 1.3 Lifecycle: `TorService`, then `TorManager`, then `AppServices`

- **`TorService`** (`amethyst/…/ui/tor/TorService.kt`) implements `TorBackend` (`TorBackend.kt`).
  - Data dir: `<filesDir>/arti`. SOCKS port: `DEFAULT_SOCKS_PORT = 17392`; if it is taken, the
    service tries the next port.
  - Polls bootstrap every 500 ms (`BOOTSTRAP_POLL_MS`).
  - Reads `guards.json` through `ArtiGuardState` to detect a poisoned guard sample.
  - Exposes `bootstrapInFlight`, `bootstrapProgress`, `guardsDownSignal`,
    `reset`/`resetWithCleanState` and `hasBootstrappedBefore`.
- **Android status type.** `amethyst/…/ui/tor/TorServiceStatus.kt` has
  `Active(port)`, `Bootstrapping(port)`, `Connecting` and `Off`. `socksPort` counts `Bootstrapping`
  as routable, and `isFullyBootstrapped` is true only for `Active`.
- **`TorManager`** (`amethyst/…/ui/tor/TorManager.kt`, 646 lines) holds the policy:
  - it combines `torType`, `externalSocksPort`, `sessionBypass` and `resetEpoch` into `status`;
  - INTERNAL calls `service.start()`, EXTERNAL emits `Active(externalPort)`, OFF stops the
    service;
  - self-heal watchdogs: stuck Connecting, stalled download, guards down, and
    `onTorCircuitsDead()` (fed by `TorCircuitHealthTracker`);
  - `connectionFailure`, the 60 s dialog, with auto-restart once and "Use regular connection" for
    an hour;
  - `isTorReady()` and `isSocksReady()`.

  **Verified: it imports nothing Android.** Its only imports are `commons.tor.TorPreferencesPort`,
  `TorType`, quartz `Log` and kotlinx.coroutines. The only JVM-specific bit is the default
  `nowMs = System::currentTimeMillis`.
- **Wiring** (`amethyst/…/AppModules.kt:393-394`): `TorService(appContext, applicationIOScope)`,
  then `TorManager(torPrefs, torService, applicationIOScope)`.
- **Mapping to shared state** (`amethyst/…/ui/platform/AndroidAppServices.kt:80-97`):
  - `torBootstrapped = torManager.status.map { it.isFullyBootstrapped }`;
  - `torStatus` maps Android's status to commons' `TorServiceStatus`, which has no
    `Bootstrapping` (`Bootstrapping`/`Connecting` both become `Connecting`);
  - `torStuck = torManager.connectionFailure`.

  Desktop fills the same three from `DesktopTorManager` (`DesktopAppServices.kt:75-77`).
- **Android-only extras.** `TorProgressNotifier` (the opt-in notification, gated by
  `AppPlatform.hasTorProgressNotification`, false by default) and `TorConnectionFailureDialog`.

### 1.4 Routing decisions

**Relays: `TorRelayState`** (`commons/src/jvmAndroid/…/tor/TorRelayState.kt`).
- It folds `TorSettingsFlow` plus relay classification (`trusted`, `dm`, `moneyOp` (saved and
  ad hoc), `signer` (saved and login), `assumed`) into `flow: StateFlow<TorRelayEvaluation>` and
  `shouldUseTorForRelay(url)`.
- `AccountsTorStateConnector` (jvmAndroid) feeds the sets from every logged-in account.
- The decision itself is `TorRelayEvaluation.useTor`, which is **already in commonMain**
  (`commons/src/commonMain/…/tor/TorRelayEvaluation.kt`). The order is:
  1. OFF: never Tor;
  2. localhost: direct if it is the user's own relay, else the new-relay policy;
  3. overlay (0200::/7): never Tor;
  4. `.onion`: `onionRelaysViaTor`;
  5. moneyOp, DM, trusted, signer, assumed relays: each its own setting;
  6. anything else: `newRelaysViaTor`.
- Why `TorRelayState` is still jvmAndroid (verified): it takes a `DualHttpClientManager` only for
  `okHttpClientForRelay(url)`. Everything else is pure flows.
- `AppModules.kt:694-710` is the relay socket: `BasicOkHttpWebSocket.Builder`.
  - `httpClient = okHttpClientForRelays.getHttpClient(shouldUseTorForRelay(url))`.
  - `canDial` holds back Tor-routed relays until `torManager.isTorReady()`, or until the session
    bypass is on.
- `RelayProxyClientConnector` (jvmAndroid) re-dials the relays whose transport flipped. It takes
  `StateFlow<OkHttpClient>` for the Tor and clear clients, but uses them **only as identity
  tokens** for change detection.
- `TorCircuitHealthTracker` (commonMain) is fed by `isTorRouted` and `isTorActive`.
- `MoneyOpRelayRouting` and `SignerRelayRouting` are commonMain interfaces that `TorRelayState`
  implements. iOS passes no-ops today.

**HTTP roles: `RoleBasedHttpClientBuilder`** (`commons/src/jvmAndroid/…/service/http/RoleBasedHttpClientBuilder.kt`).
- It implements `RoleBasedOkHttpClients`, the JVM `actual typealias IRoleBasedHttpClientBuilder`.
- On iOS, `IRoleBasedHttpClientBuilder` is an **empty** `actual interface`
  (`commons/src/iosMain/…/IRoleBasedHttpClientBuilder.ios.kt`). Every iOS actual that takes it is a
  stub. Verified for `PreviewTextFetch.ios.kt` (returns `null`), `MediaSizeProbe.ios.kt`
  (`NoSize`) and `RoutstrApi.ios.kt` (unsupported). Others are listed in §3.4.

| Role (Android method) | Setting | `.onion` handling |
|---|---|---|
| `okHttpClientForImage` | `imagesViaTor` | `.onion` always Tor; localhost and overlay direct |
| `okHttpClientForVideo` / `proxyPortForVideo` | `videosViaTor` | onion follows `onionRelaysViaTor` |
| `okHttpClientForPreview` | `urlPreviewsViaTor` | same |
| `okHttpClientForMoney`, `shouldUseTorForMoneyOperations` | `moneyOperationsViaTor` | same; also picks the Esplora endpoint (`BitcoinExplorerEndpoint.resolveNormalized(usingTor)`) and OTS |
| `okHttpClientForNip05`, `socketFactoryForNip05` (ElectrumX) | `nip05VerificationsViaTor` | same |
| `okHttpClientForUploads` | `mediaUploadsViaTor` | same |
| `okHttpClientForPushRegistration` | `trustedRelaysViaTor` | n/a |
| `okHttpClientForRelayDirectory` (georelays CSV) | `newRelaysViaTor` | same |
| NIP-11 / NIP-86 (`torEvaluatorFlow::okHttpClientForRelay`) | the relay's own policy | via `TorRelayEvaluation` |
| napplets, nSites, browser | `appletsAndWebsitesViaTor`, plus the per-site switch | n/a on iOS today (B9) |

**Underneath:**
- `DualHttpClientManager(ForRelays)` keeps two OkHttp clients, proxied and direct. The proxy
  follows `torManager.activePortOrNull`, a `java.net.Proxy(SOCKS)`. Pools are evicted when the
  route changes (`AppModules.kt` init block).
- `.onion` upgrades come from `OnionLocationCache` (commonMain) plus `OnionLocationInterceptor` and
  `OnionUrlRewriteInterceptor` (OkHttp, jvmAndroid).

**Presets and settings UI (shared already).**
- `torOnlyWhenNeededPreset`, `torDefaultPreset`, `torSmallPayloadsPreset` and `torFullyPrivate`,
  with `whichPreset`, in `commons/…/tor/TorSettings.kt`.
- `TorSettingsFlow`, `TorSettingsStore`, `TorDialogViewModel`, `TorWait`, and `ITorManager` (the
  desktop interface).
- `commonsUI/…/ui/tor/TorSettingsDialog.kt`, `TorSettingsLabels.kt`, `PrivacyOptionsScreen.kt`.

**Licensing audit for A (done before wiring it in):**
- Run `cargo license` (or `cargo deny check licenses`) on the iOS target. iOS may pull target-only
  crates.
- The package set did not change in the spike: 520 packages before and after. The current
  `Cargo.lock` with `--locked` did refuse the iOS build: cargo wanted to add `source`/`checksum`
  lines to 7 existing entries. B12a must commit the refreshed lock and re-run Android's
  reproducibility check (`verify-reproducible.sh`).
- `ring` (Apache-2.0 / ISC-style), `rustls` (Apache-2.0/MIT/ISC) and `tokio` (MIT) already ship
  on Android.

**Recommendation: A.** Reasons:
1. **One engine, one wrapper, one behaviour.** Android's hard-won lifecycle fixes depend on Arti
   specifics: OnDemand bootstrap, `isBootstrapped` polling, progress permille, `destroy()`
   releasing the state lock, and guard-state heuristics. With A, `TorManager`'s watchdogs and
   their tests apply unchanged on iOS. B or C would need a different status model (C-tor control
   port), so those fixes would be rediscovered.
2. **Verified to compile today** for both iOS targets with the pinned toolchain.
3. **No Xcode embedding or signing dance.** A static archive is linked into `AmethystKit`, which
   is already `isStatic = true` (`iosApp/build.gradle.kts`).
4. **Permissive licensing**, the same crates as Android, with no GPL variant to get wrong.
5. **Size** in line with Android (estimate, to measure in B12a).

## 3. Routing on iOS

### 3.1 NSURLSession (Ktor Darwin) through a local SOCKS5 port

- **Ktor already supports it.** Ktor 3.6.1's Darwin engine (the catalog has `ktor = "3.6.1"`)
  maps `engine { proxy = ProxyBuilder.socks(host, port) }` to `connectionProxyDictionary =
  {SOCKSEnable: 1, SOCKSProxy: host, SOCKSPort: port}`. Verified in
  [ProxySupportCommon.kt @3.6.1](https://raw.githubusercontent.com/ktorio/ktor/3.6.1/ktor-client/ktor-client-darwin/darwin/src/io/ktor/client/engine/darwin/ProxySupportCommon.kt).
  The proxy is set on the `NSURLSessionConfiguration` when the session is created, so it is
  **per `HttpClient`**: one session per client, and the port is fixed for that client's life.
- **Availability.** `connectionProxyDictionary` exists on iOS 7+
  ([Apple doc](https://developer.apple.com/tutorials/data/documentation/foundation/urlsessionconfiguration/connectionproxydictionary.md)).
  The K/N 2.4.21 iOS platform klibs expose it, plus `kCFNetworkProxiesSOCKSEnable` and
  `kCFProxyTypeSOCKS` (verified with `klib dump-metadata-signatures`).
- **Prior art.** iCepa's `TORController.getSessionConfiguration` sets exactly
  `kCFProxyTypeSOCKS` / `kCFStreamPropertySOCKSProxyHost` / `Port`. It deliberately uses
  `"localhost"`, not `127.0.0.1`, because with `127.0.0.1` ".onion addresses [don't resolve] *only
  on real devices* … DNS queries were leaking"
  ([TORController.m](https://raw.githubusercontent.com/iCepa/Tor.framework/pure_pod/Tor/Classes/Core/TORController.m)).
  **We must use `localhost` too, and test remote DNS on a device.**
- **Risk: silent failover to direct.** Apple DTS states the proxy system "is designed to make
  requests work when they would otherwise have failed", and documents cases (a proxy *connection
  error*) where NSURLSession **bypasses the proxy and goes direct**
  ([forum 705504](https://developer.apple.com/forums/thread/705504); that report was about PAC on
  iOS 16, SOCKS is *unverified*). For Tor that is an IP leak. Mitigations, in order:
  1. **iOS 17+: `proxyConfigurations` with `ProxyConfiguration(socksv5Proxy:)`.** Its
     `allowFailover` "isn't allowed by default"
     ([Network.ProxyConfiguration](https://developer.apple.com/documentation/network/proxyconfiguration.md)).
     The C API `nw_proxy_config_create_socksv5` is in the K/N Network klib (verified).
     `NSURLSessionConfiguration.proxyConfigurations` is **not** in the K/N 2.4.21 Foundation klib
     (verified absent). Set it through a tiny Objective-C shim in cinterop, or by KVC, and spike
     which one works.
  2. **iOS 16:** do not let a Tor-routed request start unless the SOCKS port is up. Android's
     `canDial` gate does this, and B12d extends it to HTTP. Add the B12f leak test below.
  3. Or raise the deployment target from 16.0 (`project.yml`) to 17.0 for Tor builds. That is a
     maintainer decision.
- **WebSockets.** Ktor Darwin opens upgrades with `webSocketTaskWithRequest` on the **same
  session** (verified in
  [DarwinSession.kt @3.6.1](https://raw.githubusercontent.com/ktorio/ktor/3.6.1/ktor-client/ktor-client-darwin/darwin/src/io/ktor/client/engine/darwin/internal/DarwinSession.kt)).
  Whether `NSURLSessionWebSocketTask` honours a SOCKS `connectionProxyDictionary` is
  **unverified**. A third-party write-up says WebSocket tasks ignore the *system HTTP* proxy;
  nothing was found either way for SOCKS. **This is the first spike (B12a).** If it fails:
  - `proxyConfigurations` (iOS 17) may cover it;
  - otherwise, a relay socket on `ktor-network` raw TCP through our own SOCKS5 handshake.
    `ktor-network` 3.6.1 publishes `iosArm64`/`iosSimulatorArm64`, Apache-2.0 (POM verified).
    TLS on top would need a TLS stack; Network.framework `nw_connection` with
    `nw_privacy_context_add_proxy` is in the K/N klib (verified) and does TLS natively.
- **ATS.** The Info.plist has **no `NSAppTransportSecurity`** (verified in
  `iosApp/xcode/project.yml`). Most `.onion` relays are plain `ws://`, and onion sites `http://`,
  and ATS blocks both. Today this already blocks any `ws://` relay on iOS. We need an ATS
  exception. Whether `NSExceptionDomains` accepts the `onion` TLD with `NSIncludesSubdomains` is
  *unverified*. The fallback is `NSAllowsArbitraryLoads`, which App Review asks to justify.
  Spike it in B12a.

### 3.2 A Ktor `IRoleBasedHttpClientBuilder` for iOS

The iOS counterpart of `DualHttpClientManager` is `DualKtorClients`, in `commons/iosMain` (or
`nonJvmMain` if wasm wants it):
- `direct: HttpClient(Darwin)`;
- `tor: StateFlow<HttpClient?>`, rebuilt when `torManager.activePortOrNull` changes. The old client
  is `close()`d, which calls `finishTasksAndInvalidate`.

`RoleBasedKtorClients` becomes iOS's `actual` face of `IRoleBasedHttpClientBuilder`, with the same
method set as `RoleBasedOkHttpClients` (`ktorClientForImage(url)`, `…Video`, `…Money`, `…Nip05`,
`…Uploads`, `…Preview`, `…PushRegistration`, `…RelayDirectory`, `proxyPortForVideo`).
- **Move the `shouldUseTorFor*` decisions out of `RoleBasedHttpClientBuilder` into a commonMain
  `TorRoleRouting(torSettings)`.** They are pure functions of `TorSettingsFlow` and
  `RelayUrlNormalizer`. Android and iOS then share one decision table.
- When Tor is wanted but there is no port yet, return a **failing** client, never `direct`.
  (Android falls back to Orbot's 9050 by accident; see the `TorServiceStatus.socksPort` KDoc.)

| NIP-05, LNURL, Cashu mint, Esplora | `Ktor*Transport { httpClient }` | → `{ ktorClientFor…(url) }`, plus `BitcoinExplorerEndpoint.resolveNormalized(usingTor = shouldUseTorForMoneyOperations(…))`, which today is hard-coded to `usingTor = false` |
| Relays | `KtorWebSocket.Builder(httpClient = { httpClient })` | `httpClient = { url -> if (torRelayState.shouldUseTorForRelay(url)) tor else direct }`, plus a `canDial` gate like Android's. `KtorWebSocket.Builder` has no `canDial` today; add one. |
| NIP-11 / NIP-86 | not wired on iOS (`Nip86Executor.None`) | per-relay client from `TorRelayState` |
| Napplets, nSites, browser (WKWebView) | not on iOS yet (B9) | WKWebView proxying is iOS 17+ through `WKWebsiteDataStore.proxyConfigurations` (*unverified*); plan it in B9. |
| ElectrumX (Namecoin) | not on iOS | raw TCP, so the SOCKS handshake goes on `ktor-network`, or `nw_connection` with a privacy-context proxy |

## 5. Risks

1. **Traffic going direct when it should not.**
   - NSURLSession falls back to direct on some proxy errors (§3.1).
   - AVPlayer ignores proxies (§3.3).
   - Any code path that still uses the single `httpClient` leaks.

   Mitigations: delete `IosAppModules.httpClient` once the roles exist, so nothing can grab it.
   Use iOS 17 `proxyConfigurations` with failover off. Add the fake-SOCKS assertion tests.
2. **WebSocket tasks may not honour SOCKS** (unverified). B12a decides; the fallback transport
   costs a week.
3. **App Store review.**
   - Embedding Tor in-process is shipped by Onion Browser and Orbot iOS (prior art; review policy
     not re-verified here).
   - Export compliance: the app already uses standard crypto, but Tor adds its own. Answer the
     encryption questions accordingly (*unverified* whether anything changes).
   - `NSAllowsArbitraryLoads` would need justification.
   - A Network Extension (option D) would need an extra entitlement and review. We avoid it.
4. **Background execution.** iOS suspends the app and its in-process Tor. On resume, circuits and
   sockets are gone. The status must not claim `Active` with a dead listener; B12f re-probes on
   foreground. Push notifications (B-step for APNs) arrive outside Tor anyway.
5. **Memory.** Arti's RSS on iOS is unmeasured. The main app has far more headroom than the 50 MB
   Network Extension limit Orbot fights. Measure in B12a. Android-side lessons (thread explosion,
   native heap) are in memory notes.
6. **Reproducible builds.** Adding an FFI face must not change the Android `.so` bytes. Gate it
   behind a feature and run `verify-reproducible.sh`. The iOS archive needs its own pinned
   toolchain story. Xcode's clang compiles `ring`/`sqlite` C code, so pin the Xcode version in
   `tools/arti-build`, as the NDK is pinned.
7. **Repo size.** Two 17 MB static slices per Arti bump. Prefer building in CI, or a release asset
   checked by SHA-256, over committing.
8. **`TorType.EXTERNAL` on iOS.** Another app cannot expose a SOCKS port that iOS keeps alive for
   us. Orbot iOS is a VPN (its README shows no SOCKS API). Hide EXTERNAL on iOS, or relabel it
   "Orbot VPN" (meaning OFF here, with Orbot routing the device).
